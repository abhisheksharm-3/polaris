# Polaris 1.15.0 — two sessions, two runs

The ledger is what makes Polaris routing bind instead of suggest. A phase is done only with its
artifact on disk and its hash matching, and four hooks read that record to decide what may run next.
It held one open run per project.

One per project reads as a safety property. It was a coincidence of implementation: the pointer
naming the open run lived at exactly one path, `.polaris/runs/.open`, and a project has one of those.
Open a second Claude Code session in the same repo and the second `seed` came back with `run 'x' is
already open; /polaris:pause clears it` — an instruction to abandon a run the other conversation was
in the middle of.

So the second session did the obvious thing and worked without a run. Outside the ledger, `assert`
has nothing to check, `guard-phase` has no phase to refuse against, and `advance-flow` names no next
step. The enforcement Polaris exists to provide was available to whichever session started first.

## What the invariant was actually protecting

Not one run per machine. One answer per conversation.

The hazard is a `PreToolUse` gate reading a different ledger than the dispatch it is gating. Two
ledgers in one conversation means two answers to "what phase is this", and the gate then allows
whatever the more permissive one says. Two conversations are two independent answers by
construction, and neither one is wrong.

That reframes the whole thing as a scoping question: find a key that is stable across everything
inside one conversation and distinct between conversations.

## The key, and the probe that qualified it

`CLAUDE_CODE_SESSION_ID` is in the environment of every `Bash` call. The open question was subagents:
a phase dispatches an agent, that agent runs `run-state.sh`, and if it saw a different id the ledger
would vanish underneath it.

It does not. A subagent was dispatched to echo the variable, and the value came back byte-identical
to the parent's. `CLAUDE_CODE_CHILD_SESSION=1` is also set and carries no distinct id, so it is not a
per-agent discriminator.

That is what qualified the key, and it is worth being explicit that it was measured rather than
assumed. A gate and the agent it gates now provably read the same pointer.

```
.polaris/runs/.open-bf215f30-21ab-4e5f-941d-59d2ffd06e98
```

`POLARIS_SESSION` overrides it, which is how the test suite drives several sessions from one process.

## The race that a second refusal closes

Two sessions can now both seed. Nothing stopped them from seeding the same slug, and two
conversations recording phases into one `state.json` is precisely the corruption the hash invariant
cannot detect: both writes are well-formed, both hashes are real, and the record is a blend of two
runs.

`seed` refuses a slug whose directory already exists. `clear` removes that directory, so a directory
that is there is owned by a live run somewhere, and the second caller picks another name. The
per-session limit is untouched: one conversation still gets one run.

## Upgrading mid-run

A run open under 1.14.0 sits at the old shared path, which nothing would read again — the upgrade
would silently orphan work that had already earned approvals.

The first session to ask adopts it:

```bash
[ -e "$OPEN" ] || [ ! -f "${RUNS}/.open" ] || mv "${RUNS}/.open" "$OPEN"
```

Proved against a live run rather than a fixture. The in-flight `token-efficiency` run migrated on the
first call and still reads phase `build`, record and approvals intact.

## What this costs

Nothing reaps a pointer whose session has ended. Close a terminal mid-flow and that run stays on
disk, invisible, until someone clears it.

The old design got this for free by being in the way: a stale `.open` blocked the next run and forced
you to look at it. Parallelism trades that prompt away. There is no reaper here, because the honest
options are a heartbeat file or an age cutoff, and both guess at when a conversation is over. It is
recorded as a known limit instead of papered over.
